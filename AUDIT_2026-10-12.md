# MDDT Agent OS — source security review

2026-10-12. This review describes the fork's pre-fix baseline; the evidence hashes identify its source files, not the subsequent OS-02 edits. Verdict: privacy-sensitive defaults and open dependency advisories require changes before a release with confidential workloads.

## Scope and evidence

Focused static review of the fork's reporting paths, provider extensions, filesystem confinement, credential storage, update configuration and their callers; lockfile advisory query through `pnpm audit --json` (pnpm 11.25.0, exit 1 due to reported advisories). No dependency installation, build, model request, exploit execution or packet capture. The installed application and live user profile are excluded by the owner's scope correction. This is not an exhaustive audit of all source, dependencies or platform behavior.

`AUDIT_EVIDENCE_2026-10-12.json` records source locations and hashes from the pre-fix baseline at the fork's initial roadmap commit; its line numbers and findings describe that historical source, not the changed working tree. Current file links below are navigation only and may now point to corrected defaults. `AUDIT_DEPENDENCIES_2026-10-12.json` retains the registry response. Findings describe code/configuration capabilities; none establishes that a particular user's data was transmitted or that the project is malicious. The default-off changes and remaining risks are tracked in [OS-02](OS-02-PRIVACY-SPEC.md) and [the handoff](HANDOFF.md).

## Findings

### F1 — P1: default-on provider extension uploads canonical session history

At the reviewed baseline, [session-log-deepseek configuration](packages/session/session-log-deepseek/src/index.ts) enabled the contribution by default; the fork's OS-02 change now disables it. Its preparation reads `snapshotEvents` after the accepted watermark, builds headers including cwd and preset, and serializes complete event data: user/system/developer messages, tool results and assistant events. The default field limit is 8 MiB per request. [Request extension serialization](packages/llm/llm-deepseek/src/request-extensions.ts) merges these fields with the model request body; [the adapter](packages/llm/llm-deepseek/src/adapter.ts) sends the result to the configured DeepSeek-compatible endpoint.

The upload is conditional on using that adapter with the extension enabled, not an autonomous upload of every session to every provider. However, canonical history can contain material no longer present in the current compacted model context, including earlier tool output or work done under another model. Choosing a provider should not silently authorize this additional history export. Recommended change: default off in MDDT compositions, explicit per-session export permission and clear payload disclosure; tests must cover model switches and compacted history.

### F2 — P2: desktop usage analytics enabled without an account-login requirement

At the reviewed baseline, [the web/desktop bundle](packages/bundle/web-app/cordis.patch.yml) mounted product analytics for Desktop with `enabled: true`; OS-02 changed the shipped default to `false`. [ProductAnalytics](packages/client/product-analytics/src/index.ts#L30) accepts events while its collection policy is enabled and adds stored device/user identifiers when available, OS version and application version. It does not require a signed-in account before emitting. [The product collector](packages/host/product-telemetry-otel/src/index.ts#L47) defaults to a DeepSeek service URL.

[Declared product events](packages/client/product-analytics/src/events.ts) include launch, model switches, session IDs, compaction, installation and update events. These declared fields do not include ordinary chat message content. Package names can still reveal custom/private components. Recommended change: disable developer analytics by default for the fork and expose an explicit optional policy with a documented field list. Session telemetry settings alone do not disable this mechanism.

### F3 — P1: feedback can export history; built-in redaction is pass-through

At the reviewed baseline, [Session telemetry](packages/session/session-telemetry-otel/src/index.ts) defaulted to FEEDBACK_ONLY and created an on-demand coordinator with `includeHistory: true`; OS-02 now defaults to DISABLED, while explicit FEEDBACK_ONLY retains that behavior. A canonical feedback submission triggers capture; merely mounting the plugin does not upload all conversations. [Redaction](packages/session/session-telemetry/src/coordinator.ts#L206) is a waterfall whose default returns the record unchanged; the seam explicitly ships no redaction rules. The reviewed source search found no production redaction listener outside the seam itself.

A feedback action can therefore disclose earlier conversation/tool material, not just the rated answer. Recommended change: default off for confidential workloads, show what is included before export, and install tested redaction if export is enabled. Feedback-only is not equivalent to anonymized.

### F4 — P1: Workspace Write is not confidentiality isolation for credentials

[SandboxedFileSystem](packages/fs/fs-sandbox/src/index.ts#L7) fences mutations but permits reads in every mode. [The macOS Seatbelt profile](packages/sandbox/sandbox-local/src/profiles.ts#L52) starts with allow-default and denies writes; it does not establish a read allowlist or an outbound-network allowlist. [Credential storage](packages/credentials/credentials-local/src/index.ts#L702) uses owner-only 0600 files and refuses group/other permissions on POSIX, but those permissions do not distinguish the Host from same-user tools or plugins.

A same-user filesystem tool or enabled plugin can access readable credential files; a prompt rule telling it not to is not an enforcement control. This is a documented design limitation, not proof of a working exploit or an observed credential leak. Recommended change: introduce an enforced read policy for sensitive resources and process-level credential isolation for untrusted executors. Preserve normal approval controls. Test with synthetic canary credentials, never real secrets.

### F5 — dependency advisories need applicability assessment

The lockfile query returned 12 advisories across nine package names: 5 high, 6 moderate, 1 low, 0 critical. These are advisory entries, not twelve demonstrated exploitable runtime bugs.

| High advisory package | Reviewed path | Applicability |
| --- | --- | --- |
| vite 5.4.21 | website development dependencies | Reported filesystem-deny bypass is Windows-specific; not proof of macOS packaged-app exposure. Update the website toolchain and review other Vite advisories together. |
| extract-zip 2.0.1, two advisories | Desktop Electron extraction and primary-runtime archive/wheel preparation | Build/supply-chain surface. Source uses the affected extractor; exploitation depends on archive control and existing verification. Hash-verified wheels reduce exposure without removing the advisory. |
| node-forge 1.4.0 | webserver -> selfsigned, declared as devDependency | Do not describe this as a production TLS vulnerability without establishing a reachable vulnerable signature-verification call. |
| http-cache-semantics 4.2.0 | electron-builder/@electron/get download stack | Build dependency; private/cacheable authenticated-response prerequisites need assessment. Registry reports patched >=4.3.0. |

Moderate reports include esbuild, Vite, uuid, fflate and sprintf-js; the low entry is retained in the raw response. fflate's malformed ZIP64 report reaches the external document/runtime dependency chain and needs separate call-site review. Missing patched versions in the registry response do not prove that no remediation exists. Do not run an automatic lockfile-wide audit fix without compatibility checks.

## Additional checks and limitations

- Installation analytics [sanitize URL, Git and local-path inputs](packages/client/ui-plugin-manager/src/client/sanitize-install-input.ts), rather than forwarding those raw strings. Click and result call sites use that helper; this limits one suspected disclosure path.
- At the reviewed baseline, the DeepSeek adapter sent attribution and persistent installation/Session identifiers alongside the request; OS-02 now requires opt-in for the persistent identifiers while ordinary app attribution remains. [Plugin inventory](packages/llm/plugin-package-inventory-deepseek/src/index.ts) contributes package names/versions to this adapter; this is separate from chat content and should be optional in the fork.
- Production update configuration names `download.deepseek.com`; local packaging defaults to the test deployment and can omit publishing configuration. A fork release needs its own verified update identity/feed or updates disabled. The audit does not establish an automatic vendor update of a locally built fork.
- Credential grants, private user files, live network traffic and installed binary equivalence were not examined. Native modules and all transitive code were not reviewed. The advisory check queried public package metadata only.

## Required follow-up

1. Disable unsolicited developer reporting and session-history extensions in the fork's default compositions; add negative tests proving no export with policy off.
2. Implement a visible export policy, then test feedback and provider changes using synthetic history containing canary secrets.
3. Enforce read restrictions and separate executor credentials; test filesystem, shell and plugin paths.
4. Triage and remediate dependencies with targeted checks, keeping build/dev/runtime distinctions.
5. Qualify an isolated source-built application with controlled traffic before claiming that only chosen model endpoints receive data.

No application code or installed settings were changed by this audit. Findings remain open; fixes and a source-build traffic check are separate work.
